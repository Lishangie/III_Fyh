## 2. Постановка задачи и контекст

### 2.1. Предметная область и задача

В банковской сфере кредитный скоринг — один из ключевых процессов: при поступлении заявки на кредит необходимо быстро и точно оценить вероятность того, что клиент не вернёт заём. Ошибка в сторону одобрения приводит к финансовым потерям, ошибка в сторону отказа — к упущенной прибыли и потере клиентов.

**Пользователь сервиса:** кредитный аналитик или автоматизированная система банка, которая отправляет параметры заявки и получает оценку риска.

**Сценарий использования:** при поступлении новой кредитной заявки система автоматически оценивает риск дефолта и рекомендует категорию риска (низкий, средний, высокий).

### 2.2. Формулировка задачи в терминах ML/ИИ

- **Тип задачи:** бинарная классификация
- **Входные данные:** 20 признаков кредитной заявки (смешанные типы: числовые и категориальные)
  - Числовые: срок кредита (duration), сумма (credit_amount), возраст (age), и др.
  - Категориальные: статус счёта (checking_account), кредитная история (credit_history), цель кредита (purpose), и др.
- **Целевая переменная:** класс заёмщика (1 = хороший, 0 = плохой / дефолт)
- **Ограничения:**
  - Интерпретируемость: кредитный аналитик должен понимать, почему модель приняла такое решение
  - Скорость: предсказание должно быть быстрым (< 100 мс на запрос)
  - Баланс ошибок: в кредитном скоринге False Negatives (пропущенный дефолт) обычно стоят дороже, чем False Positives (отказ хорошему клиенту)

### 2.3. Целевые метрики качества

- **ROC-AUC** — основная метрика; позволяет оценить качество классификации при разных порогах, устойчива к дисбалансу классов.
- **F1-score** — учитывает и precision, и recall; особенно важен, учитывая несимметричную стоимость ошибок.
- **Recall (по классу дефолта)** — важно не пропустить плохих заёмщиков.
- **Precision (по классу дефолта)** — важно не слишком часто отказывать хорошим клиентам.

Выбор ROC-AUC как основной метрики обусловлен тем, что она позволяет сравнивать модели независимо от выбранного порога классификации, что критично в задаче кредитного скоринга, где порог может меняться в зависимости от кредитной политики банка.

## 3. Данные

### 3.1. Источник данных

Используется открытый датасет **German Credit Risk** из репозитория UCI Machine Learning Repository, доступный через OpenML:

- **Ссылка:** https://www.openml.org/d/31
- **Лицензия:** открытый датасет, свободный для использования в исследовательских и образовательных целях
- **Объём:** 1000 записей, 20 признаков + 1 целевая переменная

### 3.2. Структура данных

Датасет содержит 20 признаков, описывающих кредитную заявку:

| Признак | Тип | Описание |

| savings_account | категориальный | Сбережения / гарантии |

| residence_since | числовой | Время проживания (лет) |

**Целевая переменная:** класс заёмщика (1 = хороший, 0 = плохой)

### 3.3. Предобработка и EDA

Основные шаги предобработки:

1. **Загрузка данных** из OpenML с помощью `sklearn.datasets.fetch_openml`
2. **Переименование признаков** в человекочитаемый формат
3. **Кодирование целевой переменной:** исходные значения 1 (хороший) → 1, 2 (плохой) → 0
4. **Кодирование категориальных признаков:** Label Encoding для всех моделей (13 категориальных признаков)
5. **Масштабирование числовых признаков:** StandardScaler для линейных моделей и нейросети
6. **Разделение выборки:** 70% train / 15% validation / 15% test со стратификацией

Ключевые наблюдения из EDA (подробности в `notebooks/01_eda.ipynb`):

- **Дисбаланс классов:** 70% хороших заёмщиков vs 30% плохих — moderate imbalance
- **Распределение сумм кредита:** правоскошенное, медиана ~ 2,300 DM, есть выбросы > 15,000 DM
- **Возраст:** большинство заёмщиков 20-40 лет, есть длинный хвост до 75 лет
- **Срок кредита:** медиана 18 месяцев, с пиками на «круглых» значениях (12, 24, 36)
- **Корреляции:** длительность и сумма кредита положительно коррелируют; возраст и срок — слабо

## 4. Модели и подходы

### 4.1. Базовые (baseline) модели

В качестве baseline были обучены следующие модели с гиперпараметрами по умолчанию:

1. **Logistic Regression** — простая, интерпретируемая линейная модель; служит точкой отсчёта
2. **Decision Tree** — базовая древовидная модель, склонна к переобучению

### 4.2. Улучшенные модели и эксперименты

3. **Random Forest** — ансамбль деревьев решений; более устойчив к переобучению
4. **Gradient Boosting (sklearn)** — последовательный ансамбль, часто показывает лучшие результаты
5. **MLP Classifier** — простая нейросеть (2 скрытых слоя по 64 и 32 нейрона)

Для каждой модели проводился подбор гиперпараметров с помощью GridSearchCV / RandomizedSearchCV на валидационной выборке.

### 4.3. Нейросетевая модель

Архитектура MLP:
- Входной слой: размерность = количество признаков после One-Hot Encoding
- Скрытый слой 1: 64 нейрона, ReLU + BatchNorm + Dropout(0.3)
- Скрытый слой 2: 32 нейрона, ReLU + BatchNorm + Dropout(0.2)
- Выходной слой: 1 нейрон, Sigmoid

Особенности обучения:
- Optimizer: Adam, lr=0.001
- Loss: BCELoss
- Batch size: 32
- Epochs: 50, early stopping (patience=10)
- Scheduler: ReduceLROnPlateau

Детали экспериментов — в `notebooks/02_baselines.ipynb`.

## 5. Экспериментальный протокол и результаты

### 5.1. Экспериментальный протокол

- **Разделение выборки:** Stratified split 70/15/15 (train/val/test)
- **Кросс-валидация:** 5-fold StratifiedKFold на train для подбора гиперпараметров
- **Метрики:** ROC-AUC, F1, Precision, Recall — вычисляются на отложенной test выборке
- **Воспроизводимость:** `random_state=42` во всех экспериментах

### 5.2. Сравнение моделей по метрикам

| Модель | ROC-AUC | F1 | Precision | Recall | Время обучения (с) | Комментарий |
|--------|---------|-----|-----------|--------|---------------------|-------------|
| Logistic Regression | 0.80 | 0.81 | 0.75 | 0.88 | 0.1 | Базовый baseline, хорошая интерпретируемость |
| Decision Tree | 0.66 | 0.77 | 0.80 | 0.74 | 0.01 | Переобучается, низкий AUC |
| **Random Forest** | **0.82** | **0.84** | 0.77 | **0.91** | 0.3 | Лучшая модель по ROC-AUC |
| Gradient Boosting | 0.81 | 0.83 | 0.80 | 0.86 | 0.5 | Хороший результат, немного уступает RF |
| MLP Classifier | 0.57 | 0.82 | 0.70 | 1.00 | 0.03 | Нестабильный, плохо разделяет классы |

### 5.3. Выбор финальной модели

**Финальная модель: Random Forest**

Обоснование выбора:
1. **Наивысший ROC-AUC (0.82)** — модель лучше всего разделяет классы при различных порогах
2. **Высокий F1 (0.84)** — хороший баланс precision и recall
3. **Наивысший Recall (0.91)** — важно для кредитного скоринга, где пропуск дефолта стоит дорого
4. **Приемлемое время обучения (0.3 с)** — достаточно быстро для переобучения на новых данных
5. **Время предсказания < 5 мс** — соответствует требованиям к скорости сервиса
6. **Интерпретируемость через feature importance** — можно объяснить, какие признаки влияют на решение
7. **Устойчивость к переобучению** — ансамблевая модель, менее склонная к переобучению чем одиночное дерево

Random Forest превосходит Logistic Regression по качеству на 2 п.п. по ROC-AUC и при этом остаётся достаточно быстрым и интерпредируемым. Gradient Boosting показывает близкий результат (0.81), но Random Forest демонстрирует более высокий Recall, что критично в задаче кредитного скоринга. MLP Classifier показал нестабильные результаты (ROC-AUC = 0.57), что может быть связано с малым объёмом данных и чувствительностью нейросетей к гиперпараметрам.

## 6. Архитектура решения и сервис

### 6.1. Архитектура пайплайна

```
Клиентский запрос (JSON)
    │
    ▼
FastAPI Service (app.py)
    │
    ├── Валидация входных данных (Pydantic)
    │
    ├── Предобработка признаков (preprocessing.py)
    │   ├── Label Encoding категориальных признаков
    │   └── Масштабирование числовых признаков
    │
    ├── Предсказание модели (predict.py)
    │   ├── Загрузка модели из artifacts/model.pkl
    │   └── Вычисление вероятности дефолта
    │
    ├── Определение категории риска
    │   ├── prob < 0.3 → "low"
    │   ├── 0.3 ≤ prob < 0.6 → "medium"
    │   └── prob ≥ 0.6 → "high"
    │
    ├── Логирование запроса и результата
    │
    └── Ответ клиенту (JSON)
        ├── default_probability
        ├── risk_category
        └── model_name
```

### 6.2. API и endpoints

| Endpoint | Метод | Описание | Вход | Выход |
|----------|-------|----------|------|-------|
| `/health` | GET | Проверка работоспособности | — | `{"status": "healthy", "model_loaded": true}` |
| `/predict` | POST | Предсказание риска дефолта | JSON с признаками заявки | `{"default_probability": float, "risk_category": str, "model_name": str}` |
| `/model-info` | GET | Информация о загруженной модели | — | `{"model_name": str, "model_version": str, "features": int}` |

### 6.3. Технологический стек

- **Язык:** Python 3.10+
- **ML-фреймворк:** scikit-learn
- **API-фреймворк:** FastAPI + Uvicorn
- **Валидация данных:** Pydantic
- **Логирование:** Python logging
- **Контейнеризация:** Docker
- **Работа с данными:** pandas, numpy

## 7. Наблюдаемость, конфигурация и безопасность

### 7.1. Логи и наблюдаемость

- **Логирование запросов:** каждый запрос к `/predict` логируется (timestamp, входные параметры, результат)
- **Логирование ошибок:** исключения и ошибки валидации логируются с уровнем ERROR
- **Health-check:** эндпоинт `/health` возвращает статус сервиса и информацию о загруженности модели
- **Формат логов:** структурированный формат с timestamp, уровнем, сообщением

### 7.2. Конфигурация

- **configs/config.yaml** — параметры модели и сервиса (пороги риска, гиперпараметры, порт)
- **configs/.env.example** — шаблон переменных окружения
- Все настраиваемые параметры вынесены в конфиг, что позволяет менять поведение без изменения кода

### 7.3. Безопасность

- Реальные секреты (API-ключи, пароли) **не коммитятся** в репозиторий
- Используется `.env.example` вместо реального `.env`
- Файл `.env` добавлен в `.gitignore`
- Датасет не содержит персональных данных третьих лиц (открытый, анонимизированный)

## 8. Ограничения и дальнейшая работа

**Текущие ограничения:**
- Используется один датасет (German Credit Risk) небольшого объёма (1000 записей)
